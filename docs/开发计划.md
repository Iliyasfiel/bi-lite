## 0. 三条贯穿全程的纪律

1. **e2e 是唯一门禁。** 每阶段收尾必须全绿 —— 全量跑，不是只跑改动那一段。只测新路径，等于把既有的回归防线（版式保真、金额兜底、受众分级）悄悄拆掉。
2. **断言值必须来自独立算法。** 判例见 `AGENTS.md` §6.1：B4=765345 那个错值被写进断言后，测试反而成了 bug 的守卫。**每个新加的数字断言**都要能指向"用另一条路算一遍"。
3. **接口全绿 ≠ 功能可用。** 判例见 `AGENTS.md` §6.2：三个 bug 都是浏览器里点出来的。每阶段收尾要真走一遍人的路径，不能只看接口。

## 2. 迁移策略：原地演进（已定）

**直接在 v1 上改** —— 不另起 v2 内核、不另开库文件。

**为什么可行**：`npm run e2e` 本来就是 `rm -rf data/bi.duckdb` 从空库跑（`AGENTS.md` §3）。**测试路径上不存在"迁移"问题**，每次都是重建。真正要搬的只有 `data/` 下的生产库，而它的源 Excel 一直在手上 —— **重灌一次即可**。架构 §5.6 的"影子表 + 回填 + 原子切换"因此降级成一次装载，不需要为一次性动作写长期维护的迁移代码。

**代价（要认）**：同一个库上做破坏性变更，**中间态不可回退**，且没有第二份副本可对照。所以纪律要更严，见下。

### 2.1 原地演进的纪律

- **一个库、一个门禁。** 不新建弱测试；改完 schema 就跑全量 e2e。
- **破坏性变更一次做完。** 加 `scenario_key` / `ccy_key` 这类改主键的动作，要在**一个阶段内**完成"改 DDL + 改装载 + 改查询 + 改断言"，不跨阶段留半拉子。
- **每个阶段收尾必须 e2e 全绿才继续** —— 不允许"先欠着，下一阶段一起修"。
- **改动前先 `git commit`。** 原地演进没有第二份可回退的副本，回退点只有 Git。
- **生产库重灌，不写迁移脚本。** 数据可重建是这套设计的性质（架构 §4.3 第 3 条、戒律 2）。

### 2.2 P5 的对拍怎么做（没有第二个库了）

口径拆解是全计划里唯一"错了不报错"的地方，**对拍不能省**。原地演进下这么做：

**把 `period_type` 列留到 P5 收尾。** 切换期间它仍在事实表上，于是同一条查询有两条路：

- **旧路**：直接 `WHERE period_type = '本年累计'` —— 直接查列，是**独立算法**；
- **新路**：走新的 scenario / 时间窗口 / calculator 改写。

两条路的数字必须一致，且**期望值取自旧路的 SQL**，不是新路自己跑一遍的输出 —— 否则就重演 `AGENTS.md` §6.1 那个"测试成了 bug 守卫"的判例。对拍通过后才删 `period_type` 列。

## 3. 阶段

顺序遵循架构文档 §10：**先跑通一条端到端的数据流，再去抽象生成器。** 反过来做的结果通常是抽象出一套没人用的元模型。

### P1 —— 一条端到端的数据流（朴素生成器）｜M

**目标**：Excel → raw → stg → dim → fact，**可重放**。生成器先写死，不抽象。改动落在 v1 现有文件上（`src/db/schema.ts`、`src/ingest/`），**不新建并行目录**。

> **进度**
>
> ① **着陆层**（`src/land/raw.ts` + `raw_file` / `raw_cell` + `src/paths.ts`）—— e2e 第 16 阶段：
> `file_hash` 幂等（同文件跑两次 → 一格都不重写）、round-trip 与工作簿逐格一致（含 `value_kind`
> 与公式文本）、白名单外的路径被拒、**返回值结构上只有计数与哈希**。
>
> ② **接入层改为从 raw 读**（`src/land/read.ts` 的 `rawWorkbook()` → `dryrun.ts` 的 `openBook?`）
> —— e2e 第 17 阶段：
> - **对拍**：从 raw 读 ≡ 直接读工作簿，形状逐字段相同；
> - **决定性证据**：把 raw 里某个值格改坏（测试里刻意模拟腐蚀，用完还原），接入层读到的形状
>   跟着变 —— 只断言"两边相等"是不够的，**两条路都不被使用时它们也相等**；
> - **重放**：清空 `fact_finance` 后用同一份 raw 重建两次，事实行逐行（含金额）完全相同。
>
> 落库那条路**必须先着陆**：着陆失败就抛错，不留一份不可重放的导入（铁律 12 的同理）。
> 干跑仍**一次库都不写** —— 已着陆就读 raw，没着陆就读工作簿。
>
> ③ **装载顺序守卫**（e2e 第 18 阶段）。这一刀是**看代码看出来的，不是计划里排的**：
> `run.ts` 原来写的是 `assigned.get(\`company|${r.company}\`)!` —— 取不到时 `lit(undefined)`
> 会拼出**字符串 `'undefined'`**，于是事实行指向一个不存在的主数据，**而且一个错都不报**。
> 这就是架构 §6.1 点名的"最经典的静默故障"，而且比那边更阴：丢行至少行数会少，**脏 id 连行数都是对的**。
> - 改成 `dimIdOf()`：取不到当场抛，报出第几行、哪个名字；
> - `inserted` 改成**真正落库的行数**（原先数的是"尝试插入的行数"，
>   `ON CONFLICT DO NOTHING` 安静少写的那些会被算成成功）；两者不一致即抛；
> - e2e 在**真实库**上断言不变式（无孤儿事实行 / 无 NULL 与 `'undefined'` 键），不只信代码里那个 if。
>
> **还没做**（按该先做谁排）：
> 1. **`stg_*` 标准化层**。目前 raw → fact 是 `dryrun.ts` 一步到位的；把标准化拆成独立的、
>    可整表重算的一层是架构 §6.1 ③ 的内容，等 P2 的声明层一起做。
> 2. **阶段 2 不在事务里**（写维度 → 写事实 → 改批次状态，是几条独立 `execute`）。
>    所以文档里"全有或全无"目前只到**关卡**为止：关卡 1/2 与撞库预检会把整批拦在写之前，
>    但一旦开始写，中途失败会留下**半个批次**（我的新守卫抛错时就是这么说的）。
>    修法是把阶段 2 的库写包进 `BEGIN`/`COMMIT`（Parquet 归档要挪到 COMMIT 之后 ——
>    `exportParquet()` 另开只读实例，与事务里的主库拿不到锁）。
> **④ 源文件被删也能重放**（e2e 第 20 阶段）。原先 raw 按**内容** hash 定位，
> 源文件一丢就再也找不回它对应的 raw —— 而源文件恰恰是最容易丢的东西。
> 新增 `raw_source(source_path PK → file_hash)`：**路径 → 最近一次着陆**，多对一。
> - 为什么不给 `raw_file` 加一列：同一份文件可能被拷到另一个路径传进来，
>   而 raw 是按内容去重的，于是「哪个路径对应哪份 raw」是多对一 —— 加列只能记下第一个路径；
> - **复用（reused）时也要记路径**，否则「同一份文件换个路径」这条路照样找不回；
> - `findRawFile()` 两步：文件在 → 按内容找（最准）；文件不在 → 按路径找最近一次；
> - 顺带修掉 `dryRunIngest` 的一道堵口：它在读 raw **之前**先查源文件是否存在，
>   于是「源文件删了也能重放」永远到不了；现在有 `openBook`（值从 raw 来）就不再要求文件在。

**交付**
- `src/land/raw.ts`：`file_hash` 幂等 + `raw_cell` 写入。坐标解析**复用** `ingest/dryrun.ts` 的网格展开（它已经在做"坐标 → 事实行"）。
- `src/db/schema.ts` 拆两层：**基础元数据 DDL**（`_model` / `_model_dep` / `_ingest_batch` / `_meta_objects` / `_meta_columns` / `_dq_result`，手写、不生成）+ **由声明生成的业务表**。
- **不改现有表的粒度**：P1 沿用 v1 的 `dim_company` / `fact_finance(fin_month, company_id, metric_id, period_type)`，只**新增** `raw_file` / `raw_cell` 等着陆层与元数据表。

  > ⚠️ 事实表粒度（`scenario_key` / `ccy_key` 入键）**只在 P5 改一次** —— 那里有 §2.2 的对拍兜底。提前到 P1 会让 `spec/` / `semantic/` / `render/` / `mcp/` / e2e 在同一个切片里全部失效，而那时还没有对拍能证明改对了。
- **承接铁律 16**：两档主数据归并（Tier 1 自动且留痕 / Tier 2 只给候选）必须在重写的装载层里重建，不能因为重写就丢掉。
- **CLI 骨架 + 引擎侧命令**（`src/cli.ts`、`package.json` 的 `bin`，见 §7.3）—— P1 的验收靠它跑最直接。

**验收**（这几条是 P1 的全部价值，缺一条算没做完）
- 同一份文件跑两次 → 行数不变（`(org_key, period_key, metric_id, scenario_key, ccy_key)` 幂等；架构 §4.3 第 1 条）。
- **重放**：删掉 `stg` / `dim` / `fact`、只留 `raw` → 能完整重建（戒律 2）。
- **顺序断言**：故意让维度装载晚于事实装载 → 必须**报错**，不许静默丢行（架构 §6.1 那条"最经典的静默故障"）。
- 跨批次冲突默认 **reject**（架构 §6.2 的注意块），不许悄悄覆盖。
- 金额不进任何返回值：`raw` 侧走与 `callTool()` 同款的兜底扫描。

**主要风险**：把 `raw_cell` 做成"又一次导入"而不是"重放的唯一依据"，它会变成第二份真相。判据：**清洗逻辑一律不许往回写 raw。**

### P2 —— 生成器抽象：IR + plan / apply｜L

**目标**：`models/*.yml` → IR → plan（人可读 diff）→ apply（DDL + 注册元数据）。

**交付**
- `src/gen/ir.ts` —— IR 定义。**这是让生成器可维护的关键**，没有它生成器会退化成字符串拼接（架构 §5.1）。
- `src/gen/parse.ts` —— YAML → IR（JSON Schema 语法校验 + catalog / schema 语义校验）。
- `src/gen/plan.ts` —— 读 `information_schema` + `_model` → diff → 人可读变更清单（含架构 §5.4 那个 `! 依赖检查`）。
- `src/gen/apply.ts` —— plan → DDL；写 `_model` / `_model_dep` / `_meta_columns` / `_meta_objects`。
- CLI 挂上生成器子命令：`bilite plan` / `bilite apply`（骨架已在 §7.3 立好）。
- 把 P1 手写的两张表**改由声明产生** —— 这一步本身就是 P2 的验收。

**验收**
- **幂等**：apply 之后再次 plan → 空 diff。
- **自省不漂移**：apply 后 `_meta_columns` 与 `information_schema` 逐列一致。这是语义层与 Agent 目录的**共同地基**。
- 加列 → plan 只报那一列 → apply 后**数据不重写**。
- `plan` 与 `apply` 必须是**两条命令**：先见 diff 再决定落地（架构 §5.4 的安全阀）。

**主要风险**：IR 被写薄（直接映射 YAML 字段）→ 等于没有 IR。判据：**换一种 YAML 写法，不该改 IR 以下的东西。**

### P3 —— 五种模板铺开 + 语义层自省｜L

**目标**：新增一张模板 = 选一种模板 + 填声明，**不改生成器代码**（架构 §5.3 的判据）。

**交付**
- `raw_*` / `dim_*` / `map_*` / `fact_*` / `agg_*` 五种模板齐备。
- `map_*`：`dim_business_line` + `map_org_bl`（含权重）+ `dim_statement_line` + `map_metric_stmt`。铁律 8 的运营指标（业务线 / 合同）在这里落，**不要塞进 `fact_finance`**。
- `agg_*` 全量重建（DuckDB 无 matview，重建即满足"删了能回来"）。
- `sem_metric` / `sem_dim_ref` / `sem_lineage` / `sem_caliber` + 查询改写器。
- 语义层自省：`_meta_columns.role='measure'` → 自动可选指标；`role='dim_fk'` → 自动可用维度。

**验收**
- 新增第三种事实表（如 `fact_contract`）**不改 `gen/` 里任何文件**。
- **铁律 17 原样迁移**：量纲维必须被钉住。新语义层若允许"没有 `base_fact` / 没有 caliber 的指标"，`rows: org / cols: period` 那一格又会返回一个同量级错数。**判据只能有一份**：`lint` / `plan` / Web 诊断 / `validate` 调同一个函数（铁律 17 的漂移判例）。
- 一句"2024 年按板块的税前利润，IFRS 口径，集团币"能改写成一条带 scenario / ccy 的 SQL（架构 §7.3）。

**主要风险**：语义层又长出一套自己的元数据（人工登记"现在有哪些指标"）。判据：**语义层只从 `_meta_columns` 自省，不新增第二份登记表**（架构 §7.1）。

### P4 —— 目录接口 + validate（把素材给 Agent）｜M

**目标**：架构 §8.5 落地 —— Agent 不再只有一份写死的 skill。

**交付**
- `bilite catalog dump --format=prompt|jsonschema`（带 `asOf` / `ddlHash` / `truncated`）。
- `bilite catalog show <object>` —— **按需下钻是默认路径**。
- `bilite validate <file.yml>` → `→ 建议改为：…`；引用不存在 → error；目录过期 → `CATALOG_STALE`。
- `bilite skill export` —— 从 IR 能力反推 schema，**取代 `skills/bi-lite-ingest/SKILL.md` 作为 Agent 判据**（该文件降级为人读的导览）。
- CLI 的物料侧挂载见 **§7**（骨架与切法）。

**验收**
- **零金额**：导出过金额兜底扫描；`measure` 列的 `min` / `max` / `sample` 一律不出现；`_meta_objects.row_count` 允许。
- **`_ingest_batch` 不在导出里**（已定，见架构 §8.5.2）。
- **素材与判据分离**：把 catalog 快照改旧 → `validate` 必须报 `CATALOG_STALE`，而不是照旧通过。
- L1 / L2 / L3 三层各有断言。
- 校验与生成**消费同一份 schema**（断言：`schema.json` 里有的，`validate` 都认识）。

**依赖与并行**：依赖 P2 的 `_meta_columns`，**最早可在 P2 收尾时先出只含 L2 的版本**，让 Agent 侧提前联调。

**主要风险**：目录从"结构快照"膨胀成"运营日志"（被拦掉的 `_ingest_batch` 就是这个苗头）。

### P5 —— 正交维度与口径二分（切换点）｜L｜**最高风险**

**目标**：把 `period_type` 五值拆成三件，`scenario` / `ccy` 入键，切换事实表。

**交付**
- `dim_scenario` / `dim_currency` / `fx_rate`。
- 口径二分落地（架构 §7.4 的判据）：
  - 本年累计 / 去年同期累计 / 账面累计 → **时间窗口，实存**（含审计调整，累加不等，**不许派生**）；
  - 单月 → 粒度本身；

**验收**
- **对拍**：旧路（直接 `WHERE period_type = …` 查列）与新路（scenario / 时间窗口 / calculator）数字一致；**期望值取自旧路**，不是新路自己跑一遍（否则重演 `AGENTS.md` §6.1 判例）。

## 7. CLI：与阶段并行的一条线

`需求与架构.md` §11 把 **CLI 入口列为「还没做的」第 1 条** —— 它是三个入口（CLI / MCP / Web）里唯一没实现的，`package.json` 连 `bin` 都没有。**它不是某个阶段的附带产物**，所以单列一条线，与 P1–P6 并行推进。

### 7.1 命令面（三组，按能力就绪顺序落地）

| 组 | 命令 | 依赖 | 落地 |
|---|---|---|---|
| **引擎侧**（现有能力，只是还没命令行） | `bilite ingest lint\|dry-run\|run` · `bilite render` · `bilite query` | 现有 `src/ingest`、`src/render`、`src/semantic` | P1 期间 |
| **生成器侧**（新架构） | `bilite plan` · `bilite apply` | P2 的 `src/gen` | P2 |
| **物料侧**（给 Agent） | `bilite catalog dump\|show` · `bilite validate` · `bilite skill export` | P2 的 `_meta_columns`、P4 | P4 |

> 三组共用**一个** `src/cli.ts` 骨架：先立骨架（argv 解析、`--help`、退出码、错误走 stderr），各组只是往里注册子命令。**骨架没立，P1/P2/P4 会各自发明一套参数解析** —— 那就是三份判据的开端。

### 7.2 已定：CLI 自己持有 DuckDB（方案 A）

这是 CLI 唯一的架构问题，**不定就写不出 `bilite apply`**。

`需求与架构.md` §3 写的是：

> 不要让第二个进程打开这个 `.duckdb` 文件（包括只读）。**服务端是唯一入口**；CLI 若需要读，应通过服务端而非自己开库。

但**现有代码不是这样**：`src/mcp/server.ts` 是独立进程，它 `import '../db/index.ts'` 并**自己开库**。也就是说「服务端是唯一入口」在今天的实现里并不成立 —— 按 `AGENTS.md` §1「文档即规范」，这条不一致必须收敛，不能留着。

| | A 库优先（推荐） | B 走服务端 | C 自动降级 |
|---|---|---|---|
| 做法 | CLI 自己 `open()` 库，用完退出；与 Web / MCP 同构 | CLI 只发 HTTP 请求，库由服务端独占 | 先试开库；锁被占就转 HTTP 打已在跑的服务端 |
| 互斥由谁强制 | **DuckDB 的锁天然强制**（第二个进程连只读都拿不到锁） | 需要保证服务端在跑 | 同上，外加一层"该走哪条"的判断 |
| 代价 | 服务端在跑时 CLI 用不了（须明确报错） | 要为 `plan/apply/ingest/render` **全部新开 HTTP 路由**；脚本与 CI 都依赖一个常驻服务 | **A 与 B 的成本都要付** |
| 与现状 | 一致（Web、MCP 都自己开库） | 冲突（还得把 MCP 一起改成走服务端） | 一致（A 是它的默认分支） |

**C 不推荐**，理由不是成本，而是**它会制造静默歧义**：同一条 `bilite query`，有时打本地库、有时打服务端；若两者状态不同（服务端连着另一个库文件、或数据版本不同），结果会不一样而用户无从察觉 —— 这正是本仓库最恨的那类失败（`AGENTS.md` §6.2）。

若确实想同时支持两种，正确做法是 **A 为默认 + 一个显式开关**（如 `--via-server`），并要求 CLI **始终回报它走的是哪条路**；**自动降级不做**。

**结论：选 A（已定）。** 三个入口同构（都是薄壳 + `open()`），互斥由 DuckDB 的锁兜底，第二个进程拿到明确报错即可。B 想守的「服务端唯一入口」，在单写者模型下本来就是锁在保证；而 B 要多付一条 API 面 + 两个入口行为不一致。

**规范文本已同步**（`需求与架构.md` §4.4 末，改了并留下理由）：

> 同一时刻只有一个进程持有 `.duckdb`。三个入口（Web / MCP / CLI）都自己开库，靠 DuckDB 的单写者锁强制互斥；被占用时**不静默失败**，明确报错并提示改用已在运行的入口。

### 7.4 验收（CLI 自己的门禁）

- `--help` 与各子命令的 `--help` 可用；**退出码有意义**（0 成功 / 非 0 失败），错误走 stderr。
- 引擎侧命令与 MCP / Web **走同一份判据**（`lint_ingest` / `diagnoseSpec` / `queryMetrics` 调同一个函数）—— **不许为 CLI 另写一份校验**（`AGENTS.md` 铁律 17 的漂移判例）。
- `bilite query` 的受众由入口钉死 = **human**（同铁律 10）；**不许给 agent 视角、不许有能选 agent 的开关**。断言见 §7.5。
- 库被占用时明确报错，**不静默失败**（铁律 12：不许裸 `catch`）。
- e2e 新增一段：**用 CLI 跑通一条完整链路**（ingest → query → render），断言它与 HTTP / MCP 两个入口的结果一致。

### 7.5 安全：CLI 是**人**的入口，不是 agent 的第二条取数路

方案 A 下 CLI 自己开库、直接取数（`bilite query` 返回**精确值**，与 Web 看板同级）。这是对的 —— 人就是要看精确值。但它同时意味着：**CLI 一旦被 agent 的手册"收编"，铁律 1 就被绕过**，而且绕过得很顺手（精确值、无阈值、无 `minSupport`，比 MCP 工具还好用）。

三件事要说清。

**① 受众按入口钉死，且不可被参数覆盖（同 Web）。**
`bilite query` 固定 `audience='human'`，**不提供任何能选 agent / 调精确度的开关**。Web 入口当年就是把请求体里的 `audience` 无条件覆盖掉（`AGENTS.md` 铁律 10），CLI 照抄这条。
断言：不存在 `bilite query --audience agent` 这类调用；即便传了也无效果。

**② agent 侧的一切物料里，不许出现 CLI 的取数命令。**
这条最容易漏，也最致命。skill 是 agent 的行动手册 —— 只要里面写一句"要看数可以 `bilite query`"，就等于**亲手给 agent 开了一条官方泄漏路径**。
- `skills/bi-lite-ingest/SKILL.md`（手写版）：只讲写 YAML，**不讲取数**。
- P4 的 `bilite skill export`（取代手写版）：**导出物里不得包含 CLI 的取数命令** —— `query` / `render` 是人的命令，不是 agent 的。
- 断言：skill 导出产物中**不出现** `bilite query` / `bilite render` 字样。

**③ 残余风险要写下来，不许假装没有。**
CLI 没有开新洞，也堵不上已有的洞：agent 若在**持有 `data/` 的机器上有 shell**，它本来就能绕开一切 —— 直接读 `.duckdb`、读源 Excel、或 `node -e` 调 `src/semantic/query.ts`。本设计防的是**便利路径**（让 agent **正常、被指引的工作流**永远不需要金额），不是物理隔离。
这与铁律 1 的已知局限同款写法（那里承认过：分档串与真正的低额金额都过不了 `AMOUNT_TRIPWIRE`）。**把局限写出来比声称"万无一失"安全** —— 后者会让人卸下本该保持的警觉。

> 判据一句话：**CLI 可以被人用来取数；但 agent 的官方工作流里，不能存在一条指向它的路。**

### 7.6 借鉴 DSH 的几处（已核对 `@deepseek-ai/dsh` 的 CLI 实现）

抄**形状**，不抄**机件**。DSH 是插件生态（CLI 拆成 `dsh` / `dsh-cmdline` / `dsh-commands` / `dsh-native-command` 多个包，用 commander + cordis 注入）；bi-lite 是单一小引擎、**零依赖**（`AGENTS.md` §8）。下面每条只取结构与判据。

| # | DSH 的做法 | 为什么它对 bi-lite 也成立 | bi-lite 里怎么落 |
|---|---|---|---|
| 1 | `parseDshArgs(argv) → {mode, …}` 是**纯数据**，再由 `runCli` 按 `mode` 分派 | 解析层可单测，**不必启动任何东西** | `parseCliArgs(argv): Invocation` 写成纯函数；e2e 用它在**不碰库**的前提下覆盖整个命令面（`--help` / 退出码 / 参数校验） |
| 2 | 每个 mode 里 `await import(...)` **惰性加载** | `--help` 不该加载重依赖 | `bilite --help` **不得**加载 `@duckdb/node-api`（原生插件）与 `xlsx-populate`；顺带保证"help 绝不碰库" |
| 3 | stdout = 结果，stderr = 进展与诊断（推理走 stderr、结果走 stdout；另有 `--json`） | **bi-lite 已有同款纪律**：MCP 服务端"stdout 是协议通道，日志一律走 stderr" | 三条命令同一规则：`query` / `render` 的数据走 stdout，日志与进度走 stderr，脚本可 `>` 直接接管道。这让 §7.5 的"数据只有一条出口"更硬 |
| 4 | 启动失败：stderr 一行结论 + 完整诊断落私有日志（`mode 0600`、`flag wx`）；**写不成就把全文打回 stderr，不许声称已保存** | 正是铁律 12 的形态（Parquet 归档静默失效那次的判例） | "库被占用"这类失败：stderr 一行可读结论 + 详情落 `data/logs/`。**"没写成就不许声称已保存"照抄** |
| 5 | `hasAction()` 结构性守卫 —— 忘了 action 的 program 会"解析成功、什么都不发布"，失败形态是**静默空转** | bi-lite 的立场：宁可在入口响亮失败，也不要安静地什么都不干 | `src/cli.ts` 命令表自检：注册了却没有 handler → **启动即报错**；e2e 加一条断言 |
| 6 | 退出走注入的 `appExit`，不散落 `process.exit()`；`configureExitAndOutput` **递归到子命令** | bi-lite **已有先例**：`src/server.ts` 导出 `start()/stop()` 供 e2e 进程内起服务 | handler `return` 结果、退出码由一处决定；e2e 能在进程内跑 CLI 而不杀测试进程 |

**还有一条不是抄、是佐证**：`@deepseek-ai/dsh-headless` 的定位写着 "a direct core runner over `dsh-base` with **no Host, HTTP, or browser layer**" —— 非交互入口直连内核、绕过 Host/HTTP。**这正是 §7.2 方案 A 的先例**：CLI 自己持有库不是特例，而是同构的姊妹入口。

**明确不抄的**：

- **argv 所有权分层 / pass-through**（`dsh --profile web -h` 打的是 web 的 help）—— DSH 有"启动器 + 内层 app"两段结构，bi-lite 没有，不需要。
- **commander 与 cordis 注入** —— 违反"零依赖"。bi-lite 命令面只有约 9 条固定子命令，手写解析足够。
- **多包拆分** —— 那是插件生态的产物。bi-lite 就是**一个** `src/cli.ts` + 按组拆的命令模块。
- **结构性地判 `CommanderError`（不用 `instanceof`）** —— DSH 是为了"外部插件带着自己的 commander 副本"；bi-lite 单仓零依赖，不存在这个问题。

> 核对方式与局限：读的是 `@deepseek-ai/dsh` v0.2.0-rc.2 的 `lib/bin.js`、`@deepseek-ai/dsh-cmdline/lib/index.js`、`@deepseek-ai/dsh-headless/lib/index.js`。这些是**打包产物**（无 `.ts` 源、无 sourcemap），之所以可读是因为 **JSDoc 被保留**了 —— 所以上面判断的依据是**编译后代码 + 注释**，不是原始源码。

### 第 1 片（已完成）：新路径补齐 + 新旧对拍

**这一片什么都没删**，只是把"新路径配不配取代旧路径"这件事证明掉。结果是：**它本来不配。**

把同一份 960 行长表交给两条路对拍（期望值取自旧路），第一次就撞出**四处能力缺口**：

| # | 缺口 | 补法 |

| ① | 期数不认**完整日期** `2026-01-01` | `parsePeriodText` 放宽到含日期/时间，**但保留 `$` 锚点与年月范围校验** |

### 第 2 片顺带挖出的产品级缺陷：归档会把库锁丢掉（已修）

**症状**：e2e 里从第 15 阶段起的**每一份**归档都是**空文件**（960 行的批次写成 222 字节，
只有表头没有行），而 `archived` 仍报 `true`。起因就是新加的那条"归档可读"断言。

**根因链**（每一步都实测过，完整记录见 `AGENTS.md` §4 备忘 13 与 `需求与架构.md` §4.4.1）：

1. `exportParquet()` 的**短命只读实例一关，主实例的库锁就没了**（`CHECKPOINT`/空查询都拿不回来，
   只有"关掉重开主实例"能拿回）。
2. 于是第 13 阶段的 **MCP 子进程能开进主库**（它本该被锁挡住）→ 库上出现**两个写者**。
3. 两个写者 → 主实例后续的归档全部读到**过期视图** → 空归档 + `archived: true`。
   （另一面：只读实例是"创建那一刻的快照"，留着不关能保锁但数据陈旧 —— 两条路都试过。）

**修法**（三件，都在这一片里）：
- `exportParquet()` 用完只读实例后调 **`reattach()`**：把主实例关掉重开，把锁拿回来。
- `exportParquet()` 新增 **`verify`**：写完在**同一个只读实例**上 `read_parquet` 数一遍，
  对不上就抛错 → `archived` 置 false。**"安静的错"变成"响亮的错"。**
- **e2e 第 13 阶段**不再让 MCP 子进程开主库，改成给它一份**库的副本**
  （`CHECKPOINT` 后字节拷贝 = 一致快照）+ 新增的 `BILITE_DB` 环境变量指过去。
  这才符合文档里的模型：**一个进程一个库**。

**为什么这一片值得记**：一个"只读、同进程、用完即弃"的辅助实例，实则是**会改变跨进程状态边界**的
操作。原始推理（"它是只读的，所以伤不到主库"）只看了**谁能写数据**，没看**谁持有锁**。

## 11. 第四刀：期数的**日期格**（`keys[].type: date`，2026-10-01）

退场那三片之后剩的最后一项"新路径要成为旧路超集"的能力：**真实的 Excel 日期格期数列**。

**为什么不能"自动判断"**（这是本切最关键的一个判断）：
`xlsx-populate` 把日期格给成**序列号**（实测 `2026-06-01` → `46174`），
而 raw 里存下的也正是这个数字（`value_kind=number, raw_value=46174`）——
**"它是日期格"这件事压根没存**。若引擎靠读 xlsx 的 `numFmt` 来判断，
**首灌（读 xlsx）与重放（读 raw）就会得出不同的期数**，而那会直接违反"raw 是值的唯一依据"。
所以把解读写成**声明**：`keys: [{ col: A, as: period, type: date }]`，两条路读的是同一份事实。

**做了什么**
- `keys[].type: 'text' | 'date'`（默认 text，写别的词报 `KEYS_TYPE_BAD`，不许静默退回默认读法）。
- `excelSerialToDate()`：序列号 → 年月日，**只支持 1900 系统**；序列号 < 61 一律拒绝
  （Excel 凭空算进了 1900-02-29，1..59 与 ≥61 的基准差一天 —— 而这里**差一天就是差一个月**）。
- **1904 日期系统一律拒绝，两处**：打开源文件（`openSourceForIngest`）与**着陆之前**（`landRawFile`）。
  后者的理由值得单记：raw 存得下序列号、存不下日期系统，那种 raw 会变成"重放得出另一个答案"的陷阱。
  xlsx-populate **不给**这个标志（实测三个可疑属性全是 `undefined`），只能自己看
  `xl/workbook.xml` 的 `<workbookPr date1904="1">`（`template.ts` 的 `usesDate1904()`）。
- 诊断文案改成人能照着做：不声明时报 `PERIOD_CELL_NOT_TEXT`，并写清两条路
  （改成文本 / 声明 `type: date`）；声明了却换不出日期时，提示改为"确认它是真的日期格"。

**数字与断言**：e2e **351 → 361**（第 27 阶段 10 条），另加两套夹具
（`接入-日期格` 1900 系统、`接入-日期格1904` 1904 系统）。第 27 阶段钉住的四件事：
① 换算与**实测基准**一致（46174 = 2026-06-01 · 25569 = 1970-01-01 · 61 = 1900-03-01）；
② 可疑序列号一律拒绝；③ 声明了才读、**不声明不猜**；④ 落库（值从 raw 来）与重放（显式从 raw 读）**得到同一份期数**。

**教训（与 §10 那次事故同源）**：写断言时我把 `109574` 当成"超出 1900–2200"，
其实它是 **2199-12-31**（在范围内）—— 门禁当场把它拦下来了。**边界值要算，不要凭印象写。**

## 12. 第五刀：报表规格补一条判据 —— 口径名必须注册过（2026-10-01）

**这一刀不是文档里列的待办**（那张表里的项都已按你的拍板推后，见 §6），而是**上一轮实测出来的缺口**：
报表规格的口径名写错时，整套判据一条不报。

**判例（先坐实，再动手）**：把 `specs/月度保送表.yaml` 里的「本年累计」改成形近的「本年度累计」——

**判据落在哪、为什么这么落**：`src/spec/lint.ts` 对 `rows` / `cols` 里 `dim === 'period_type'` 的轴，

这里不猜）。**直接引注册表，而不是像接入侧那样从调用方注入**：报表侧的口径只可能是注册表里的 id

这正是"判据只有一份"。
