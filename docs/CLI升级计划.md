# CLI 升级计划

## 目标

将 bi-lite 从依赖仓库目录的开发工具，升级为可通过 npm 安装、在独立业务工作区运行的工具。

已确认的产品选择：

- 网页打开时，agent 仍可通过 CLI 导入和生成报表。
- `bilite init` 默认建立通用空工作区，财务模型和示例按需添加。
- 开发继续直接运行 TypeScript，仅发布 npm 包时生成 JavaScript。
- `bilite web` 保留前台日志，`Ctrl+C` 停止服务，CLI 可在其他终端使用。
- CLI 保持轻量：薄入口、按需加载、普通模块组合，Web 与 CLI 复用既有引擎。

目标用法如下，包名暂沿用 `bi-lite`，正式发布前确认名称可用性：

```bash
npm install -g bi-lite
bilite --version
bilite init ./my-bi
cd my-bi
bilite web

# skill 按需安装，不作为 CLI 的使用前提
bilite skill install

# 在其他目录操作指定工作区
bilite --workspace /path/to/my-bi ingest dry-run ingest/月报.yaml
```

分发基础、工作区基础与共享执行已完成：`npm pack` 可生成 JavaScript 包，安装包可脱离源码运行；`init` 默认建立空工作区，财务模型通过 `--preset finance` 补入。
网页入口与可选 skill 安装已实现；真实安装包流程覆盖空工作区、财务预设、共享导入/出表/重放、skill 副本保护和服务恢复。
浏览器启动的成功/失败回调已做针对性验证；实际桌面浏览器行为、最低 Node 版本与其他平台仍需发布前确认。

## 1. npm 分发与全局入口

- npm 包通过 `bin` 暴露 `bilite`，安装后不要求用户克隆源码、运行 `node src/cli.ts` 或使用 `npm link`。
- 安装目录只存放引擎、网页静态资源和受版本管理的默认模型资源，不作为业务数据目录。
- 开发仍运行 `src/*.ts`；只在打包发布时转译为 JavaScript，用户安装后不需要编译器或 TS 加载器。
- npm 入口加载 `dist/` 中的 JavaScript，网页静态资源同步放入发布目录，原生 DuckDB 依赖保持外部依赖。
- 不能仅凭 `npm link` 验收：Node 原生类型擦除不支持 `node_modules` 下的 TypeScript，因此发布包必须提供 JavaScript。[Node 官方说明](https://nodejs.org/api/typescript.html#type-stripping-in-dependencies)
- 发布前按真实安装包验证最低 Node 版本，再同步 `engines`、README 与 AGENTS 的开发/发布约定，不能继续沿用未经分发验证的最低版本声明。
- 设置明确的发布文件白名单，包含运行入口、引擎、网页资源和初始化资源。用户指标、数据库、源 Excel、输出、测试产物及本地配置不进入 npm 包。
- 基础模型使用独立的发布资源，不能直接把当前工作区定制的模型/指标当作全局默认值。
- `npm link` 仅保留给开发调试；发布验收使用 `npm pack` 生成的真实安装包。

发布包建议仅包含 `bin/`、`dist/`、受控的 `assets/presets/`、skill 模板与必要说明文件。
使用 `prepack` 或等效的发布前命令生成产物，安装阶段不执行本项目的编译；不将“用户本地安装”变成开发环境搭建。

## 2. 独立业务工作区

引擎版本由 npm 安装管理，业务配置及数据归工作区管理：

```text
my-bi/
  bilite.config.json
  models/
  metrics/
  ingest/
  specs/
  templates/
  data/
  output/
  .bilite/             # 临时运行状态，不进版本库
```

- `bilite init [目录]` 只创建工作区标识和空目录，默认没有财务模型、业务指标、源文件或数据库。
- 建议用 `bilite init [目录] --preset finance` 显式添加受控的财务基础模型；已初始化的空工作区也可按同样语义补入预设，不覆盖已有模型。示例数据单独提供，不在初始化时自动导入。
- 初始化不覆盖已有文件；旧项目保留目录结构，并提供明确的兼容识别方式。
- 选择顺序：`--workspace` > `BILITE_WORKSPACE` > 从当前目录向上识别工作区标识。旧项目没有标识时，兼容在项目根目录运行或显式指定根目录。
- 所有入口先确定工作区，再加载依赖模型的业务模块；统一处理规格、模板、源文件、默认数据库和输出路径。
- 未指定工作区时，帮助和版本命令可直接使用；业务命令在未初始化目录中给出初始化提示，不能回退到安装目录写数据。
- `BILITE_DB` 等显式配置保留兼容，使用说明交代其与工作区的关系。
- 空工作区必须是有效状态：`catalog` 返回空目录，Web 展示初始化/模型设置入口，不能因为缺少 `dim_metric`、`dim_company` 或模型文件而启动失败。
- 工作区模型加载改为显式、惰性的上下文加载，处理现有 `META = metaOf(loadModels())` 等模块导入时读取配置的问题。
- 工作区文件是可编辑的业务声明，不作为可执行插件加载。源文件继续遵循工作区路径白名单。

## 3. CLI 与网页共用操作层

一个工作区同一时刻只由一个进程持有 DuckDB，CLI/Web 同时可用不意味着两个进程同时打开库文件。

```text
网页运行：浏览器 ─┐
                 ├→ 前台本地服务 → 共用操作层 → DuckDB
          CLI ───┘

未开网页：CLI → 同一操作层 → DuckDB → 结束后释放
```

- CLI 入口负责工作区解析、参数校验、选择执行方式及输出；业务逻辑仍由共用操作层执行。
- Web 启动后在 `.bilite/` 写入运行状态，CLI 通过真实路径与服务握手识别对应服务，不能只按固定端口或 PID 判断。
- 运行状态包含协议版本、工作区身份、实例标识和连接信息；退出清理，崩溃遗留状态须验证后再清理，不能误停其他进程。
- 没有 Web 服务时，CLI 获取工作区执行锁，独立执行并关闭数据库；Web 启动和其他独立 CLI 也遵守同一互斥机制。
- 获取执行锁后重新检查服务状态，避免“检查时无服务、打开库前服务已启动”的竞争；启动等待有明确超时和提示。
- Web 运行时，CLI 的数据库操作转交服务，同一操作不得再由客户端直连数据库执行。纯校验、结构查看等不需要数据库的操作可留在本地。
- 服务统一调度写入与结构变更，读请求只看到一致的已提交状态；进行结构变更时将受影响的请求排队。
- 模型/指标 YAML 在请求前按需重新读取并校验，`apply` 成功后更新上下文，不让长运行服务沿用旧的模块级目录快照。
- 网络连接中断时不盲目重试导入等写操作，应报告操作标识及可查询状态，避免响应丢失后重复执行。
- 传输只接受命名操作与结构化参数，不提供任意 SQL/代码执行；agent 操作继续只返回结构、计数、路径和状态，Web 返回人的精确结果，受众由服务入口确定。
- 本地服务仅监听回环地址，校验工作区身份、浏览器来源与本地连接凭据。MCP 保持可选适配层，后续也应复用同一执行入口与互斥约束。

### 轻量实现边界

借鉴 DeepSeek Harness 的[薄启动入口](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/src/bin.ts)、[HTTP 承载分工](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/web-server.md)与[Web 就绪后打开浏览器](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/src/index.ts)。采用普通函数和显式上下文实现这些分工，保留单一 npm 包。

| 边界 | 职责 |
|---|---|
| CLI 入口 | 参数解析为纯数据命令、定位工作区、按需加载对应处理器、输出与退出码 |
| 工作区运行上下文 | 路径、模型目录、数据库生命周期、执行互斥；按需创建并显式关闭 |
| 共用操作 | 调用现有接入、查询、编译与渲染函数，复用校验与受众边界 |
| Web 承载 | 一个 `node:http` 服务提供静态页面、浏览器 API 和 CLI 转交入口，负责启动与停止 |

- 继续使用现有 CLI 的纯数据 `Invocation` 和惰性处理器设计，检查并移除阻碍惰性加载的顶层依赖；帮助、版本和无需数据库的校验不启动 Web 或打开数据库。
- 共用操作按实际重复的业务流程逐步抽取，保留现有引擎模块。CLI 参数对象与 HTTP 请求分别转换为业务操作参数，业务层不依赖终端、HTTP 或浏览器。
- CLI 转交使用 Web 已有的 HTTP 服务，只补必要的结构化操作入口与握手；首版无需独立通信端口、通用 RPC 框架或生成客户端 SDK。
- 首版所有访问数据库的业务操作在持库进程内串行执行，以一个简单执行链保证一致性。数据库事务保持现有边界，不引入后台任务系统、持久任务队列或并发读写调度器。
- 写操作保留操作标识与最小状态；服务仍存活时可核对完成情况，重启后结合既有批次记录核对。无法确认的执行结果明确返回未知，不自动重试，不承诺崩溃后自动续跑。
- 页面资源继续使用现有 HTML、JS、CSS，随 npm 包分发，由服务按安装位置读取；用户工作区只保存业务文件。开发保持现有静态页面方式。
- 启动顺序明确为取得工作区所有权、准备运行上下文、监听并确认 API/页面就绪，再发布运行状态和打开浏览器；启动失败统一释放已取得的资源。停止采用同一生命周期清理函数。
- 功能扩展通过现有 YAML 声明与内部模块完成。本阶段不引入 Cordis、插件加载器、依赖注入容器、事件总线、profile/patch 组合体系或多包拆分。

DeepSeek Harness 的这些入口与 Web 分工提供组织方式参考；DuckDB 的单进程持库、工作区互斥和 agent 数据边界仍由 bi-lite 自身保证。

## 4. `bilite web`

```bash
bilite web
bilite --workspace ./my-bi web
bilite web --port 4320
bilite web --no-open
```

- 默认启动当前工作区的网页端并打开系统浏览器，仅监听本机 `127.0.0.1`。
- 首版以前台进程运行，终端输出工作区与访问地址，`Ctrl+C` 停止服务并释放数据库。
- CLI 在其他终端通过服务执行命令；不需要先关闭网页再导入。执行进度与排队状态使用日志/结构化结果返回。
- `--port` 指定端口，`--no-open` 只启动服务，不打开浏览器，供远程终端及自动验收使用。
- 端口被占用、数据库被其他进程占用时给出可操作提示，不启动到另一份数据库或悄悄更换工作区。
- 网页静态文件从安装包读取，上传、导入、模板和输出使用所选业务工作区。
- 同一工作区已有健康的 Web 服务时，二次执行只打开对应网页并提示服务所在位置，不启动第二个数据库实例。
- 默认端口为4319；不同工作区占用端口冲突时，首版提示使用 `--port` 指定另一个端口。CLI 从工作区运行状态获取实际地址，不假定4319。
- 浏览器打开失败时保留已启动服务并输出访问地址。停止时拒绝新写入，等待已开始的事务完成，再关闭数据库和端口。
- 首版不引入后台常驻守护进程、开机自启或远程访问；前台服务与 CLI 之间的本地通信纳入本轮。

## 5. skill 可选安装

- npm 安装不自动写入 agent 的 skill 目录、MCP 配置或全局设置。
- `bilite skill install` 显式安装项目级 skill；如需要用户级安装，再通过 `--scope user` 明确选择。
- npm 包可携带与引擎版本对应的 skill 模板，但安装与使用 skill 都不是 CLI/Web 的前提。
- skill 使用全局 `bilite` 与明确的工作区定位，不依赖源码绝对路径。
- 保留 `skill export`；没有 MCP 时仍可用 CLI 完成结构查看、接入和报表操作。
- 遇到已有 skill 不静默覆盖，说明目标路径及版本；重新安装或升级的覆盖行为需显式选择。
- 安装采用受版本管理的文件副本，不链接到 npm 安装目录，避免 npm 更新或卸载后留下失效链接。记录 skill 模板版本，更新时提示，不自动覆盖用户修改。
- 首版先支持当前项目使用的 Codex skill 目录；其他 agent 的安装适配按后续需要增加。CLI 和 Web 不依赖任何 agent 宿主。

## 6. 实施顺序与完成标准

1. **分发基础**：补齐发布转译、资源白名单与全局入口。真实 `.tgz` 安装后可从任意目录运行帮助和版本，不依赖源码目录。
2. **工作区基础**：实现空工作区、定位与财务预设，解除模块加载时对当前财务配置的依赖。旧目录可继续使用，重复初始化不覆盖业务文件。
3. **共享执行**：抽出共用操作层、服务通信与执行锁。Web 打开时 CLI 可导入/出表，独立 CLI 仍可执行，不出现双写者或错误工作区连接。
4. **网页入口**：完成 `web`、端口参数、浏览器打开、前台日志、停止与崩溃恢复。终止服务后 CLI 可独立继续使用数据库。
5. **可选 skill**：完成显式安装、版本记录与现有文件保护，手册统一使用全局命令和正确工作区。
6. **发布验收**：在 `bi-lite-test` 安装实际 npm 包，跑通本节验收后再准备发布与升级说明，不以开发链接测试代替。

## 7. 验收

复用现有主链路验收，新增一条安装包级流程：

- 用 `npm pack` 生成包，在独立安装位置安装 `.tgz`，从 `bi-lite-test` 调用 `bilite`，不依赖 `npm link`。
- 新的空工作区可打开 Web 和查看空目录；选择财务预设后可进入接入流程，初始化本身不自动导入示例。
- 重复初始化不覆盖文件；指定工作区、环境变量和从子目录运行都能定位正确，多个工作区之间数据不串用。
- 使用该工作区的数据完成试运行、导入、报送与重放，原开发库不变。
- `bilite web --no-open` 可启动并提供网页与 API；正常启动可打开浏览器；停止后端口和数据库锁释放。
- Web 保持运行时，从另一个终端通过 CLI 导入测试包并生成报表，页面可读取新提交结果；关闭 Web 后 CLI 可独立继续操作。
- 检查同时启动、端口冲突和遗留运行状态，确认只产生一个数据库持有者，不根据无效 PID 结束其他程序。
- 不安装 skill 时 CLI 与 Web 仍可用；按需安装 skill 后使用全局命令，不要求源码路径或 MCP。
- 检查包文件清单，确认不含数据库、测试源和私人配置；本轮先完成 Windows 实际验收，其他平台按实际支持范围声明。

npm 发布需在计划确认、实现及安装包验收完成后另行执行。

## 8. 方案阶段与后续待验证项

- 第 1-5 步已实现；第 6 步由 `npm run package:check` 执行实际安装包验收（隔离工作区，不读写开发数据库）。当前实测 Windows / Node 24.18.0。
- 包名、最低 Node 版本与 Windows 之外的平台支持，在发布基础阶段通过注册表检查、依赖约束与实际安装测试确定。
- 本地通信协议、执行锁和停机行为先做一条完整流程验证，再扩展边界；不建设多租户、远程服务或独立云端后端。
