# CLI 升级计划

## 目标

将 bi-lite 从依赖仓库目录的开发工具，升级为可通过 npm 安装、在独立业务工作区运行的工具。

目标用法如下，包名暂沿用 `bi-lite`，正式发布前确认名称可用性：

```bash
npm install -g bi-lite
bilite --version
bilite init ./my-bi
cd my-bi
bilite web

# skill 按需安装，不作为 CLI 的使用前提
bilite skill install

# 在其他目录操作指定工作区
bilite --workspace ./my-bi ingest dry-run ingest/月报.yaml
```

当前只有本地开发链接和工作区引导草稿，尚不能视为 npm 正式分发完成；`bilite web` 和可选 skill 安装命令尚待实现。
本次交付计划与业务测试包；全局入口草稿保留在本地，不作为本 PR 的已实现功能。后续按实施顺序推进，不发布 npm 包。

## 1. npm 分发与全局入口

- npm 包通过 `bin` 暴露 `bilite`，安装后不要求用户克隆源码、运行 `node src/cli.ts` 或使用 `npm link`。
- 安装目录只存放引擎、网页静态资源和受版本管理的默认模型资源，不作为业务数据目录。
- 首版继续使用原生 TypeScript、无构建步骤；用打包产物确认最低 Node 版本，并同步 `engines`、安装说明和错误提示。
- 设置明确的发布文件白名单，包含运行入口、引擎、网页资源和初始化资源。用户指标、数据库、源 Excel、输出、测试产物及本地配置不进入 npm 包。
- 基础模型使用独立的发布资源，不能直接把当前工作区定制的模型/指标当作全局默认值。
- `npm link` 仅保留给开发调试；发布验收使用 `npm pack` 生成的真实安装包。

## 2. 独立业务工作区

引擎版本由 npm 安装管理，业务配置及数据归工作区管理：

```text
my-bi/
  bilite.config.json
  models/
  metrics/
  ingest/
  specs/
  templates/
  data/
  output/
```

- `bilite init [目录]` 创建工作区标识、基础模型和空业务目录，不复制开发仓库的测试数据或数据库。
- 初始化不覆盖已有文件；旧项目保留目录结构，并提供明确的兼容识别方式。
- 选择顺序：`--workspace` > `BILITE_WORKSPACE` > 从当前目录向上识别工作区标识。旧项目没有标识时，兼容在项目根目录运行或显式指定根目录。
- 所有入口先确定工作区，再加载依赖模型的业务模块；统一处理规格、模板、源文件、默认数据库和输出路径。
- 未指定工作区时，帮助和版本命令可直接使用；业务命令在未初始化目录中给出初始化提示，不能回退到安装目录写数据。
- `BILITE_DB` 等显式配置保留兼容，使用说明交代其与工作区的关系。

## 3. `bilite web`

```bash
bilite web
bilite --workspace ./my-bi web
bilite web --port 4320
bilite web --no-open
```

- 默认启动当前工作区的网页端并打开系统浏览器，仅监听本机 `127.0.0.1`。
- 首版以前台进程运行，终端输出工作区与访问地址，`Ctrl+C` 停止服务并释放数据库。
- `--port` 指定端口，`--no-open` 只启动服务，不打开浏览器，供远程终端及自动验收使用。
- 端口被占用、数据库被其他进程占用时给出可操作提示，不启动到另一份数据库或悄悄更换工作区。
- 网页静态文件从安装包读取，上传、导入、模板和输出使用所选业务工作区。
- 首版保持 DuckDB 单写者约束；Web 运行期间，同库 CLI 操作提示占用。后台服务、进程复用与 IPC 不纳入本轮。

## 4. skill 可选安装

- npm 安装不自动写入 agent 的 skill 目录、MCP 配置或全局设置。
- `bilite skill install` 显式安装项目级 skill；如需要用户级安装，再通过 `--scope user` 明确选择。
- npm 包可携带与引擎版本对应的 skill 模板，但安装与使用 skill 都不是 CLI/Web 的前提。
- skill 使用全局 `bilite` 与明确的工作区定位，不依赖源码绝对路径。
- 保留 `skill export`；没有 MCP 时仍可用 CLI 完成结构查看、接入和报表操作。
- 遇到已有 skill 不静默覆盖，说明目标路径及版本；重新安装或升级的覆盖行为需显式选择。

## 5. 实施顺序

1. 收拢全局入口草稿，确定工作区配置和路径规则，补齐安装包资源布局。
2. 完成工作区初始化与旧项目兼容，确认引擎升级不会覆盖工作区配置及数据。
3. 接入 `web` 子命令、端口参数、浏览器打开及退出清理。
4. 增加可选 skill 安装，更新 skill 的 CLI 工作方式和使用说明。
5. 在 `bi-lite-test` 使用实际 npm 安装包验收；通过后再准备 npm 发布与升级文档。

## 6. 验收

复用现有主链路验收，新增一条安装包级流程：

- 用 `npm pack` 生成包，在独立安装位置安装 `.tgz`，从 `bi-lite-test` 调用 `bilite`，不依赖 `npm link`。
- 新工作区可初始化；重复初始化不覆盖文件；指定工作区和从子目录运行都能定位正确。
- 使用该工作区的数据完成试运行、导入、报送与重放，原开发库不变。
- `bilite web --no-open` 可启动并提供网页与 API；正常启动可打开浏览器；停止后端口和数据库锁释放。
- 不安装 skill 时 CLI 与 Web 仍可用；按需安装 skill 后使用全局命令，不要求源码路径或 MCP。
- 检查包文件清单，确认不含数据库、测试源和私人配置；本轮先完成 Windows 实际验收，其他平台按实际支持范围声明。

npm 发布需在计划确认、实现及安装包验收完成后另行执行。
